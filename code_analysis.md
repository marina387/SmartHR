# Анализ кода проекта SmartHR

## 1. Общая картина проекта

Проект представляет собой демонстрационное HR-приложение для:
- оценки кандидатов по вакансиям;
- просмотра и фильтрации кандидатов;
- анализа вакансий;
- демонстрации минимального RAG-пайплайна на базе документов HR-области.

Основной стек:
- Python;
- Flask;
- Pandas;
- NumPy;
- TF-IDF + собственный чанкинг/поиск (RAG-демо);
- CSV/JSON как простое хранилище данных.

---

## 2. Структура проекта

### Основные точки входа

- [app.py](app.py) — корневой Flask-приложение, которое загружает данные из CSV и предоставляет API-эндпоинты.
- [src/routes/main.py](src/routes/main.py) — более структурированный модуль маршрутов, используемый в расширенной части приложения.
- [src/cli/app.py](src/cli/app.py) — возможный CLI-интерфейс для демонстрации RAG.

### Ключевые каталоги

- [src/services](src/services) — бизнес-логика: оценка кандидатов, парсинг, шаблоны, интервью, вакансии.
- [src/core](src/core) — основной RAG-ядро: чанкинг, retrieval, pipeline.
- [src/storage](src/storage) — слой хранения данных JSON/файлов.
- [data](data) — исходные и обработанные данные.
- [tests](tests) — тесты по маршрутам, scoring и другим частям проекта.

## 3. Анализ основного приложения

### 3.1. Корневой файл app.py

Файл [app.py](app.py) является точкой входа приложения и выполняет сразу несколько задач:
- загружает CSV-файлы;
- хранит словари перевода должностей и навыков;
- формирует HTML-шаблон главной страницы;
- реализует REST API;
- запускает сервер Flask.

Сильные стороны:
- приложение быстро запускается и легко проверяется в браузере;
- API-эндпоинты простые и понятные;
- данные выводятся сразу без дополнительной базы данных.

Проблемы:
- большая часть логики находится в одном файле;
- используется глобальный state (`df_кандидаты`, `df_вакансии`) без изоляции и инициализации через фабрику приложения;
- при импорте модуля сразу происходит чтение CSV и печать в консоль;
- много русскоязычных имен переменных и малых helper-функций создают сложность сопровождения;
- отсутствие явной архитектуры и слоя сервисов на уровне корневой точки входа.

### 3.2. Endpoint-слой

В [app.py](app.py) есть маршруты:
- `/` — главная страница;
- `/api/score` — получение данных кандидата по ID;
- `/api/candidates` — список кандидатов;
- `/api/stats` — статистика;
- `/api/search` — поиск по навыкам и должностям;
- `/api/vacancies` — список вакансий;
- `/api/candidates/top` — топ-10 кандидатов.

Логика в целом понятная:
- проверяется наличие данных;
- данные преобразуются к JSON;
- результат возвращается через `jsonify`.

Однако в реализации есть повторяющиеся паттерны:
- один и тот же цикл преобразования DataFrame в dict;
- повторное использование словаря `перевод_колонок`;
- отсутствие общей функции сериализации модели.

Это снижает поддерживаемость и усложняет расширение API.

## 4. Анализ оценки кандидатов

### Сервис: [src/services/scoring.py](src/services/scoring.py)

Основные responsabilidades:
- определить статус кандидата (`green`, `yellow`, `red`);
- проверить критические фильтры;
- вычислить итоговый балл;
- формировать комментарии по критериям.

Ключевые моменты:
- `get_status_decision(total)` — удобно и понятно;
- `check_critical_filters()` проверяет наличие критических требований в тексте резюме;
- `calculate_total()` подсчитывает интегральный score по весам;
- `evaluate_stub()` использует детерминированный `random.Random(seed)`, что делает оценки воспроизводимыми.

Плюсы:
- логика легко тестируется;
- оценка прозрачна и предсказуема;
- веса и критерии вынесены в конфиг.

Недостатки:
- `evaluate_stub()` — это скорее симуляция, чем реальная оценка текста;
- система недостаточно связана с реальными данными резюме и вакансиями;
- `calculate_total()` использует `self._normalize_weights(weights)` внутри цикла и повторно вычисляет веса, что не оптимально по чистоте кода;
- оценки не используют семантическую проверку навыков, а строятся по случайному генератору на основе текста.

Итог: сервис хорошо подходит для демо-проекта, но не для production-оценки кандидатов.

## 5. Анализ RAG-пайплайна

### Модуль: [src/core/rag_pipeline.py](src/core/rag_pipeline.py)

Это компактная реализация Retrieval-Augmented Generation.

Компоненты:
- `RagPipeline` — главный объект;
- `build_index()` — разбивает документы на чанки и индексирует их;
- `ask()` — выполняет поиск релевантных блоков по запросу;
- `RagResult` — форматирует результат для вывода.

Поддерживаемые внутренние модули:
- [src/core/chunking.py](src/core/chunking.py) — разбиение текста на чанки;
- [src/core/retrieval.py](src/core/retrieval.py) — TF-IDF Retrieval.

Плюсы:
- простой и понятный минимальный рабочий пример;
- легко запускать локально;
- поддерживает демонстрацию концепции RAG без зависимости от внешних LLM.

Проблемы:
- это не полноценный RAG, а скорее поисковый MVP;
- не используются современные методы ранжирования и re-ranking;
- нужна более сильная работа с метаданными и контекстом запросов;
- без LLM нет генерации ответа, только подбор релевантных блоков.

## 6. Анализ маршрутов и веб-слоя

### Файл: [src/routes/main.py](src/routes/main.py)

Этот файл уже выглядит ближе к архитектурно организованной реализации:
- есть `Blueprint`;
- отдельные сервисы для вакансий, интервью, хранения, шаблонов и обратной связи;
- есть функция `_load_documents()` для загрузки внешних HR-документов;
- есть адаптация данных для шаблонов интерфейса.

Это заметно лучше, чем корневой `app.py`.

Плюсы:
- логика разделена по сервисам;
- есть подготовка view-модели для шаблонов;
- документация внутри функций на русском языке помогает быстро ориентироваться.

Недостатки:
- всё ещё много логики в одном файле без сильного разделения на controller/service/repository;
- есть статические глобальные объекты, которые создаются при импорте;
- хранение JSON-файлов напрямую в `data/` без полноценного слоя миграции и валидации.

## 7. Сильные стороны проекта

1. Наличие рабочей демонстрационной архитектуры.
2. Простота запуска и использования.
3. Логика оценки кандидатов уже структурирована и понятна.
4. RAG-часть дает понятное объяснение, как работает поиск по документам.
5. В проекте есть тесты, что полезно для контрольной проверки.
6. Приложение подходит для учебного и демонстрационного использования.

---

## 8. Слабые места и риски

1. Слишком много логики в [app.py](app.py).
2. Использование глобальных DataFrame и JSON без явной инициализации.
3. Отсутствие строгой типизации и единых моделей данных.
4. Риск перегруженности кода русскоязычными переменными и смешением языков.
5. Оценка кандидатов основана на детерминированном симуляторе, а не на реальном анализе текста.
6. Нет разделения на чистые слои: storage, domain, service, API.
7. Проект функционально хороший как demo, но требует рефакторинга для масштабирования.

## 9. Рекомендации по улучшению

### Архитектурные
- вынести общую бизнес-логику из [app.py](app.py) в отдельные service-модули;
- создать фабрику Flask-приложения (`create_app()`);
- перенести загрузку данных в слой startup/session;
- использовать Pydantic или dataclass-модели для структур данных.

### LLM/RAG
- расширить retrieval до hybrid-search по TF-IDF + BM25 + семантический поиск;
- добавить re-ranking;
- внедрить генерацию ответа через LLM или шаблонный summarizer.

### Data layer
- использовать SQLite/PostgreSQL вместо CSV/JSON для реального приложения;
- обеспечить валидацию и нормализацию входных файлов.

### Quality
- добавить базовые end-to-end тесты для API;
- покрыть ключевые сценарии: поиск, score, critical filters, top candidates;
- настроить форматирование и linting (Black, Ruff, Flake8).

---

## 10. Итог

Проект SmartHR — это хороший учебный и демонстрационный пример HR-аналитики и RAG-механики. По функциональности он уже выглядит рабочим, но с точки зрения архитектуры и масштабируемости нуждается в рефакторинге. В нынешнем виде приложение лучше всего подходит для демо, прототипа и обучения, чем для промышленного использования.

Если задача — сделать продуктовую систему, то главные направления: архитектурный рефакторинг, нормализация данных, более сильная логика оценки и переход от demo-хранилища к устойчивому backend-слою.
