# Целостность базы

Обучение и веса моделей эта процедура не изменяет.

SQLite в приложении включает `PRAGMA foreign_keys=ON` для каждого нового
соединения. Ссылки в ответах репозиториев берутся из реляционных столбцов,
включая NULL после удаления кандидата, а не из старого JSON payload.
Пакетное сохранение, сохранение вакансии с весами и импорт JSON выполняются
с откатом всей операции при ошибке. Это не заменяет отдельную задачу по
транзакциям бизнес-операций, вызывающих несколько сервисов.

## Проверка и исправление

Команды выполняются из корня проекта в установленном окружении:

```powershell
.\.venv-run\Scripts\python.exe scripts/repair_database_integrity.py
.\.venv-run\Scripts\python.exe run_smarthr.py --backup-only
.\.venv-run\Scripts\python.exe -m flask --app app db upgrade
.\.venv-run\Scripts\python.exe scripts/repair_database_integrity.py --apply
```

Перед исправлением рекомендуется остановить приложение и проверить процедуру
на копии (`--database путь`). Режим по умолчанию ничего не изменяет.
`--apply` создаёт резервную копию, блокирует других писателей и повторно
проверяет нарушения внутри транзакции. При неизвестном типе нарушения
вся правка откатывается. Повторный запуск на исправной базе ничего не меняет.

Записи с обязательной ссылкой на отсутствующего кандидата перемещаются в
`integrity_archive`; в нём сохраняются исходная таблица, ID, причина, время
и полная исходная строка, включая JSON payload. Они не участвуют в рабочих
отчётах и оценках. Диалоги остаются вместе с сообщениями; недействительная
ссылка снимается, а исходная строка диалога также сохраняется в архиве.
Кандидаты не создаются заново и не сопоставляются по догадке.

Архив содержит рабочие данные и не должен публиковаться. Для восстановления
отдельных связей требуется подтверждённая карточка кандидата; архив не нужно
импортировать обратно автоматически. Полный откат — остановить приложение
и восстановить резервную копию средствами SQLite (учесть изменения после копии).

## Результат проверки 22 октября 2026

Обнаружено 20 нарушений, относящихся к трём отсутствующим ID кандидатов:
13 событий этапов, 2 связи с вакансиями, 1 оценка, 1 обратная связь,
3 диалога. В старом JSON нашлись только частичные данные двух кандидатов;
в имеющейся предыдущей резервной копии всех трёх карточек нет.
Причина первоначального удаления не установлена; текущий контроль внешних
ключей сам по себе не исправляет ранее накопленные нарушения.

Выбрано сохранение 17 записей в архиве и снятие 3 недействительных ссылок
диалогов с сохранением оригиналов. На копии базы после исправления —
0 нарушений внешних ключей. Затем процедура применена к рабочей базе:
`PRAGMA foreign_key_check` — 0 нарушений, `PRAGMA quick_check` — `ok`.
Все 20 архивных оригиналов сверены с резервной копией; кандидаты, вакансии,
интервью, сообщения, действия чата и обратная связь по ответам не изменены.
Повторный запуск не вносит изменений. Восстановление вымышленных карточек
не выполнялось.

Резервная копия непосредственно перед исправлением:
`data/backups/smarthr_before_integrity_20261022_162240_983205.db`.
Проверки: 50 тестов (целостность, SQL-репозитории, системные сценарии,
архивирование кандидатов, воронка, маршруты) прошли успешно.
