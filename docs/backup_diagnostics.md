# Резервирование, восстановление и диагностика

Команды запускаются из корня проекта. В Windows вместо `python` можно
использовать `.\.venv-run\Scripts\python.exe`.

## Полная копия

Остановите сервер и выполните:

```powershell
python run_smarthr.py --backup-only
```

Сохраняются согласованный снимок SQLite через SQLite Backup API и вся папка
SMARTHR_DOCUMENTS (по умолчанию `data/documents`): каталог library.json,
загруженные файлы, их версии и JSON с исходными названиями. Манифест содержит
версию формата, время UTC, версию схемы, размеры и SHA-256 каждого файла.
Затем выполняется проверка копии. Старые копии не удаляются. Снимок переносим
одним файлом SQLite даже при исходном режиме WAL: подтверждённые записи
включаются в него, зависимость от WAL/SHM не сохраняется.

Копия появляется в новой папке `data/backups/smarthr_*`. Перед миграциями
при обычном запуске автоматически создаётся такой же комплект, если база
существует. При первом запуске без базы сохранять ещё нечего.

Запускающий скрипт отказывается делать `--backup-only`, если настроенный
локальный порт занят. Это дополнительная проверка, а не замена остановке
всех процессов приложения: не изменяйте базу и документы параллельно копированию.
Для библиотеки дополнительно проверяется отсутствие изменений во время копии.
Незавершённая копия остаётся в `.partial-*`, а не публикуется как готовая.

Копии содержат рабочие данные. Храните их приватно и сохраняйте отдельный
экземпляр вне рабочего компьютера. Код, .env, логи, датасеты и веса моделей
в этот комплект не входят. Файлы-примеры из docs/sample_docs восстанавливаются
вместе с кодом проекта. Все копии под data/backups исключены из Git.

## Проверка и восстановление

Подставьте путь, выведенный при создании копии:

```powershell
python run_smarthr.py --verify-backup "data/backups/smarthr_..."
python run_smarthr.py --restore "data/backups/smarthr_..." --restore-to "data/restores/recovery-1"
```

Проверяются точный состав, размеры, хеши и целостность SQLite, включая внешние
ключи. Повреждённая копия не восстанавливается. Манифест обнаруживает случайное
повреждение, но не заменяет шифрование или проверку подлинности источника.
Символические ссылки, junction, выходы за пределы каталога и неизвестная
версия формата не принимаются.

Восстановление допускается **только в новую папку**. Рабочая база и документы
не перезаписываются. Сначала собирается и проверяется промежуточная папка,
потом она публикуется как результат. При ошибке оригинал сохраняется;
промежуточная `.restore-*` остаётся для диагностики. Результат содержит
`database.sqlite3`, `documents` и `manifest.json`.

Для проверки восстановленной копии и последующего переключения остановите
сервер и укажите оба пути в новой PowerShell-сессии:

```powershell
$env:SMARTHR_DATABASE = (Resolve-Path "data/restores/recovery-1/database.sqlite3").Path
$env:SMARTHR_DOCUMENTS = (Resolve-Path "data/restores/recovery-1/documents").Path
python run_smarthr.py --diagnose
python run_smarthr.py
```

Сначала проверьте страницы и данные восстановленного приложения. Для возврата
к прежней базе остановите сервер и верните предыдущие значения двух переменных
(либо откройте сессию с прежней конфигурацией). Автоматическая подмена рабочих
данных при `--restore` не выполняется. Папка data/restores исключена из Git.

Ранее созданные отдельные `.db`-копии сохраняются, но не являются комплектом
нового формата: у них нет манифеста и библиотеки документов. Новая команда
восстановления предназначена для новых полных комплектов.

## Диагностика

```powershell
python run_smarthr.py --check
python run_smarthr.py --diagnose
```

`--check` проверяет зависимости. `--diagnose` читает состояние существующей
SQLite: quick_check, число нарушений внешних ключей и версию схемы. Он также
показывает наличие папки загрузок и расположение журнала. Отсутствующая база
не создаётся; неинициализированная/неисправная база даёт ненулевой код выхода.
Отсутствие папки загрузок допустимо, если документов ещё не загружали.

`GET /api/health` проверяет доступность базы и соответствие миграций коду:
200 при готовности, 503 при проблеме. Отсутствующую базу он не создаёт.
Он не запускает генерацию и не проверяет
качество ответа модели. Полный quick_check остаётся офлайн-командой,
чтобы не сканировать всю базу при каждом запросе состояния.

## Журнал

Записи JSON находятся в `data/logs/application.jsonl` или SMARTHR_LOG_DIR.
Ротация: основной файл до 1 МБ и 3 предыдущих файла. Для каждого запроса
сохраняются время UTC, endpoint, метод, статус, длительность и новый request_id.
При исключении сохраняются класс и расположение в коде, без текста исключения.

Тела запросов, тексты резюме, сообщений, SQL-параметры и query string не
сериализуются в этот журнал. Request ID создаётся сервером, а не берётся
из заголовка клиента. Он возвращается в X-Request-ID и в JSON ошибок API.
По этому ID можно найти событие ошибки, не сохраняя содержимое запроса.
Это описание журнала приложения; вывод внешнего веб-сервера настраивается
отдельно. Логи исключены из Git. Для многопроцессного развёртывания нужен
отдельный сборщик журналов; текущая ротация рассчитана на локальный сервер.

Обучение, датасеты, признаки, веса моделей и существующие рабочие записи
в этом этапе не менялись.

## Результат проверки 25 октября 2026

Прошли 309 тестов, проверка синтаксиса 60 Python-файлов и 10 JavaScript-файлов,
проверка зависимостей. Создана реальная копия рабочей базы и восстановлена
в отдельную папку: содержимое всех SQL-таблиц совпало, основные страницы
и `/api/health` открылись с кодом 200. Загруженных документов в рабочей
папке не было; сохранение каталога, предыдущих версий и файлов проверено
на отдельной тестовой библиотеке.

Контрольные суммы рабочей базы, scoring-модели и метаданных не изменились.
Проверены повреждённые копии, неизвестная версия/небезопасные пути,
режим WAL, запрет перезаписи существующей папки и краткая блокировка папки
Windows при публикации копии. При постоянной блокировке операция завершается
ошибкой, не заменяя исходные данные. Проверки инструментов обучения не запускались.
