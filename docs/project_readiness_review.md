Проверка готовности SmartHR — 21 октября 2026

Вывод: рабочий локальный прототип с заметным покрытием пользовательских сценариев. К управляемой демонстрации условно готов; к работе нескольких сотрудников с реальными персональными данными пока не готов. Оценка качественная: процент готовности без утверждённых критериев был бы условной цифрой.

Обучение не запускалось, файлы моделей и код приложения не изменялись. Проверки изменения данных выполнены в отдельных временных SQLite-базах; рабочая база читалась в режиме mode=ro. Создан только этот отчёт.

Проверено:

- Синтаксис 81 Python-файла из src, scripts и точек входа: ошибок нет. JavaScript в src/static/js проверен node --check.
- pip check: несовместимых установленных зависимостей не обнаружено. Это не сканирование известных уязвимостей.
- Полный pytest tests остановился на сборе tests/test_real_dataset_collection.py: отсутствует datasets из окружения подготовки данных.
- После исключения только этого модуля: 159 passed, 1 failed. Ошибка tests/test_model_pipeline.py:21 — тест ожидает salary_ratio, отсутствующий в текущем наборе признаков. Это подтверждает рассогласование теста и текущего контракта, но само по себе не доказывает ошибочность предсказаний модели. Ранее пройденные 124 проверки являлись подмножеством тестов.
- Миграции на пустой временной базе завершились с кодом 0, версия 7c24d3f180a1. Копирование рабочей базы через sqlite backup и чтение копии успешно: quick_check=ok, количество кандидатов совпадает. При очистке одного временного каталога возникла блокировка Windows; это ошибка очистки проверочного скрипта, а не миграции.
- Рабочая SQLite: quick_check=ok, но foreign_key_check возвращает 20 нарушений.
- Воспроизведены ошибки обработки обязательных требований, несогласованного этапа интервью и частично сохранённого переноса. Исходящие обращения при проверке URL были подменены mock; реальные запросы к внутренним адресам не выполнялись.

Наиболее важные замечания:

1. P1 — нарушена ссылочная целостность рабочей базы.

20 записей ссылаются на отсутствующих кандидатов: score_results — 1; feedback — 1; candidate_vacancies — 2; chat_conversations — 3; candidate_stage_events — 13. Физическая исправность SQLite не означает логическую целостность данных. Происхождение этих записей этой проверкой не установлено. Перед демонстрацией нужно разобраться с происхождением и восстановить либо явно обработать связи на копии, затем повторить foreign_key_check. Автоматически удалять эти записи нельзя.

2. P1 — перенос кандидата не является одной транзакцией.

src/storage/sql_storage.py:65 фиксирует каждую запись отдельно. src/services/candidate_vacancy_service.py:35 сначала изменяет исходное рассмотрение, затем создаёт целевое и аудит. Обновление основной карточки и истории оценки выполняется позже в src/routes/main.py:1372. В проверке искусственный отказ сохранения истории оценки дал HTTP 500, но исходный этап уже стал transferred, а основная вакансия кандидата уже изменилась. Повтор операции не равен безопасному повтору незавершённого переноса. Нужна единая транзакция на весь бизнес-процесс с rollback. Аналогичный риск существует для других составных операций и подтверждений действий.

3. P1 — чат сейчас не использует LLM для генерации обычных ответов.

src/chat/service.py:106 вызывает structured_answer. Все текущие сценарии из _scenario обрабатываются src/chat/responses.py и ранними ветками ChatService. В нормальных сценариях до self.model.generate выполнение не доходит. Даже TransformersChatModel.generate в src/chat/models.py возвращает шаблоны и не вызывает загруженный pipeline для генерации. Загрузка весов подтверждает загрузку, а не участие модели в ответе.

ML-scoring является отдельным механизмом и реально вызывает predict_proba в src/matching_service.py:233. Поэтому описание проекта должно различать модель соответствия и помощника с правилами, поиском и шаблонами. Если в демонстрации заявляется генерация ответов обученной чат-моделью, текущая реализация этому не соответствует. Исправление может быть изменением описания архитектуры либо отдельной задачей подключения inference; переобучение для самого вывода о проблеме не требуется.

4. P1 — неодинаковые обязательные проверки в разных путях оценки.

src/routes/main.py:1148 берёт critical_requirements из тела запроса с default=[], хотя vacancy_id указан. Вакансия передаётся scoring-сервису, но проверка критических требований получает именно этот пустой список. Подтверждено вызовом /api/score с вакансией, содержащей обязательное требование, без поля critical_requirements: сервис получил []. В ручном добавлении есть fallback к требованиям вакансии. Проверки должны иметь один серверный источник правил.

5. P2 — интервью и этап кандидата могут противоречить друг другу.

src/routes/main.py:1431: _sync_interview_stage пропускает rejected и несколько других терминальных состояний. При назначении интервью отклонённому кандидату API вернул 201 и создал запись календаря, но этап остался rejected. Требуется явное правило: запретить назначение до возврата в работу либо согласованно менять этап. Сейчас календарь и фильтр кандидатов на собеседование могут расходиться.

6. P1 для сетевого использования — доступ не разграничен, импорт URL допускает запросы на внутренние адреса.

Маршруты API не требуют входа и не проверяют права пользователя на кандидатов, историю диалогов и изменения. app.py:11 содержит известный ключ по умолчанию. Это допустимое ограничение локальной демонстрации, но не многопользовательской установки.

src/routes/main.py:1235 проверяет наличие подстроки hh.ru в URL вместо проверки hostname. src/services/parsing.py:73 выполняет requests.get с автоматическими перенаправлениями. Подтверждено через mock: /api/parse_hh принимает http://127.0.0.1:9999/internal?source=hh.ru и передаёт адрес HTTP-клиенту. Для сетевой установки нужны проверка схемы и разрешённого домена, контроль перенаправлений и запрет внутренних адресов. Реальная эксплуатация не проверялась.

7. P2 — неполная валидация API и нестабильность при параллельной работе.

/api/chat с JSON-массивом вместо объекта возвращает 500 из-за payload.get, а должен вернуть контролируемый 400. Аналогичный шаблон чтения JSON встречается в других обработчиках; их нельзя считать проверенными на все некорректные типы.

SqlRepository._next_id вычисляет max+1 по текущим данным. Без атомарного выделения ID два параллельных запроса могут выбрать одно значение. Проверка конкурентными запросами в этом аудите не проводилась, это вывод из кода. Изменение каталога документов защищено RLock только внутри процесса, индекс хранится в памяти; согласованность нескольких процессов не обеспечивается.

Не проводились нагрузочные испытания, полноценный внешний pentest, повторная оценка качества моделей на независимых данных и проверка установки на чистом другом компьютере. Качество обучения не переоценивалось; обучение и распознавание резюме не изменялись.
